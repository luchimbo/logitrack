# Plan Evolutivo GeoModi: Flujo Operativo Logistico

## Objetivo

Convertir GeoModi de una app centrada en etiquetas/envios a un sistema operativo logistico completo:

```text
pedido -> picking -> empaque -> despacho -> entrega
```

## Principios

| Fuente | Uso |
|---|---|
| Referencias de mercado | Benchmark funcional |
| GeoModi actual | Base real y diferencial |
| wiki.mormon.garden | Criterio de UX, datos, estados, roles, metricas y MVP |

## Que Mantenemos

| Modulo actual | Decision |
|---|---|
| Subir Etiquetas | Se mantiene como entrada manual/fallback |
| Parseo ZPL/TXT | Se mantiene como diferencial |
| `shipments` | Se mantiene como capa logistica |
| Print Jobs V2 | No se toca al inicio |
| Flex | Se mantiene y pasa a Despacho |
| Colecta | Se mantiene y pasa a Despacho |
| Mapa | Se mantiene y luego se conecta con entregas |
| Dashboard | Se mantiene y se amplia |
| Integraciones | Se mantienen y alimentan pedidos |
| Usuarios/workspaces | Se mantienen y se amplian con roles operativos |

## Arquitectura Interna

La app deberia evolucionar desde:

```text
etiquetas / integraciones -> shipments -> flex / colecta / picking list / dashboard
```

Hacia:

```text
etiquetas / integraciones -> orders -> order_items -> picking -> packing -> shipments / packages -> despacho
```

## Fase 1: Base De Pedidos

Objetivo: crear una capa de pedidos sin romper `shipments`.

Cambios:

- Crear `orders`.
- Crear `order_items`.
- Crear `order_shipments`.
- Agregar `operation_status`.
- Hacer que integraciones y etiquetas alimenten pedidos.
- Mantener `shipments` como fuente de etiquetas, tracking y carrier.

Resultado:

```text
GeoModi empieza a operar por pedido, no solo por etiqueta.
```

## Fase 2: Rediseno UX Y Navegacion

Objetivo: que la app se sienta como un flujo operativo.

Cambios:

- Reordenar sidebar por proceso.
- Crear `Inicio Operativo`.
- Crear vista `Pedidos`.
- Usar badges consistentes de estado.
- Reemplazar emojis por iconos SVG.
- Mejorar estados vacios, errores, carga y exito.
- Disenar picking/empaque mobile-first.
- Mantener vistas densas para supervisores/admins.

## Fase 3: Picking Por Pedido

Objetivo: sumar el core operativo de preparacion por pedido.

Funcionalidades:

- Abrir pedido.
- Ver productos, SKU, cantidades y metodo de envio.
- Iniciar picking.
- Marcar cantidades recolectadas.
- Ver progreso del pedido.
- Crear incidencia por producto.
- Finalizar picking.
- Enviar a empaque.

Tablas:

```text
picking_sessions
picking_items
operation_events
```

## Fase 4: Centro De Empaque

Objetivo: agregar estaciones y sesiones de empaque.

Funcionalidades:

- Crear estaciones de empaque.
- Asignar usuario o hacer check-in.
- Ver pedidos listos para empacar.
- Iniciar empaque.
- Agregar peso/dimensiones.
- Finalizar empaque.
- Imprimir etiqueta.
- Marcar pedido como listo para despacho.

Tablas:

```text
packing_stations
packing_sessions
packages
```

## Fase 5: Incidencias

Objetivo: resolver problemas sin perder trazabilidad.

Tipos iniciales:

```text
producto_faltante
stock_insuficiente
producto_danado
direccion_invalida
problema_etiqueta
reemplazo_producto
```

Funcionalidades:

- Crear incidencia desde pedido, item, picking o empaque.
- Asignar responsable.
- Cambiar estado.
- Agregar comentarios.
- Vincular con pedido y producto.
- Mostrar link rapido a WhatsApp si existe telefono.

## Fase 6: Analytics Operativo

North Star Metric:

```text
Pedidos listos para despacho dentro del SLA y sin incidencia
```

Metricas principales:

| Metrica | Uso |
|---|---|
| Pedidos completados por dia | Volumen operativo |
| Tiempo promedio de picking | Productividad picker |
| Tiempo promedio de empaque | Productividad packer |
| Incidencias por pedido | Calidad operativa |
| Pedidos atrasados | SLA |
| Reimpresiones | Problemas de impresion |
| Flex sin transportista | Riesgo de despacho |
| Pedidos por tienda | Performance comercial/operativa |

## Fase 7: Entregas

Objetivo: sumar un TMS liviano despues de picking/empaque.

Funcionalidades:

- Crear ordenes de entrega.
- Agrupar pedidos.
- Asignar logistica propia o tercerizada.
- Asignar chofer.
- Programar entrega.
- Marcar entregado/fallido.
- Ver progreso.
- Conectar con mapa.

Tablas:

```text
delivery_orders
delivery_order_items
drivers
```

## MVP Recomendado

| Orden | Cambio | Resultado |
|---|---|---|
| 1 | Crear `orders` y `order_items` | Base canonica |
| 2 | Vincular con `shipments` | No rompemos etiquetas |
| 3 | Crear vista `Pedidos` | Operacion unificada |
| 4 | Agregar picking por pedido | Salto funcional fuerte |
| 5 | Agregar incidencias simples | Control operativo |
| 6 | Crear empaque basico | Flujo completo hasta despacho |
| 7 | Reordenar navegacion | Mejor UX |

## Que No Hacer Todavia

- No reescribir toda la app.
- No eliminar `shipments`.
- No tocar fuerte Print Jobs V2.
- No borrar la lista de picking actual.
- No hacer reportes IA antes de tener buenos eventos.
- No construir entregas antes de empaque.
- No mezclar estados del marketplace con estados internos.
- No hacer tickets tipo chat completo en la primera version.

## Resultado Esperado

GeoModi pasaria de ser:

```text
panel de etiquetas + logistica
```

a ser:

```text
sistema operativo logistico con pedidos, picking, empaque, despacho, integraciones e impresion robusta
```

## Diferenciales Propios De GeoModi

| GeoModi | Ventaja |
|---|---|
| Etiquetas reales | Mejor base de impresion |
| Print Jobs V2 | Trazabilidad y control |
| Flex por zonas | Mejor operacion local |
| Integraciones | Mas potencial de automatizacion |
| Mapa | Mejor capa geografica |
| App propia | Mayor personalizacion |
